# The RSATB JSON input

A calculation is one JSON file and one command:

```bash
rsatb run graphene.json
```

This is the primary interface. The Python API underneath it is still there and
still supported — see [python_api.md](python_api.md) — but a JSON input is the
thing to reach for first, because it is the only form of the calculation that
can be validated, diffed, archived, and generated by something other than a
person.

## The four sections

```json
{
  "structure": { },   // where the atoms are
  "model":     { },   // what the Hamiltonian is
  "run":       { },   // how the calculation is carried out
  "tasks":     [ ]    // which observables to compute
}
```

They line up one-for-one with the objects the library is built from —
`Structure`, a `Model`, `SetupOptions`, and the `compute_*` calls — so a JSON
key maps onto a constructor argument rather than onto a private normalization
layer. `structure` and `model` are required; `run`, `tasks` and `output` have
defaults.

The smallest input that runs:

```json
{
  "structure": {"file": "graphene.vasp"},
  "model": {
    "type": "sktb",
    "basis": {"C": ["pz"]},
    "hamiltonian": {
      "onsite": {"C": {"pz": 0.0}},
      "pairs": {"C-C": {"pp_pi": {"kind": "constant", "value": -2.7, "r_cut": 1.6}}}
    }
  },
  "tasks": [{"type": "dos", "dE": 0.1}]
}
```

## The rules the format keeps

**Nothing is declared that can be derived.** The model reports the basis it
works in, so orbital counts and graph cutoffs are never input. An LCAO model
reads them from its `.orb` files; an SKTB model derives them from the radial
cutoffs. Those numbers used to be constructor arguments transcribed by hand
with nothing checking them.

**A wrong input is an error, not a different calculation.** Unknown keys are
rejected with a suggestion, enums are closed, and every check names the exact
path into the document:

```
error: run.kpoint: unknown key 'kpoint'
    hint: did you mean 'kpoints'?
error: model.spin: 'colinear' is not a supported value
    hint: did you mean 'collinear' or 'noncollinear'?
```

**One way to express each thing.** H and S are separate `SkParameters` objects,
so an SKTB model with no `overlap` is orthogonal and one with an `overlap` is
not — there is no shape to guess at.

**Options say what they do.** `preconditioner.target` defaults to `"auto"`,
which resolves from the model's own capabilities: `overlap` for a
non-orthogonal model, `none` for an orthogonal one.

**An input can explain itself.** Any key starting with an underscore —
`_comment` and the like — is carried through uninterpreted, at any level.

## The commands

| | |
|---|---|
| `rsatb doc [TOPIC]` | what an input may contain, and what each key means |
| `rsatb template NAME -o input.json` | a working input to start from |
| `rsatb check input.json` | validate: schema, files, and cross-section consistency |
| `rsatb show input.json` | the input with every default filled in |
| `rsatb run input.json` | set up and compute |
| `rsatb schema` | the same schema as JSON Schema (draft 2020-12) |
| `rsatb info` | what this build supports |

`doc`, `template`, `check`, `show` and `schema` import nothing compiled and
need no MPI, so an input can be written and validated on a laptop or a login
node and only then queued. Only `run` needs the extension. Where the console
script is not on `PATH`, `python -m rsatb.cli` is the same program.

`rsatb doc` is generated from the same declaration the validator uses, so the
documentation cannot drift from what is accepted. `rsatb doc` with no argument
prints the overview and the topic index; `rsatb doc model.sktb`,
`rsatb doc tasks.dc`, `rsatb doc run.kpoints` go into one topic;
`rsatb doc --all` prints everything.

## What `check` catches

Three kinds of problem, in three passes:

1. **Malformed fields** — a typo, a wrong type, a value outside its range, a
   missing required key, an enum that is not one of the accepted values.
2. **Files that are not there** — every path in the document is resolved
   against the input file's own directory and tested.
3. **Sections that disagree** — each is valid, but together they are not:

```
error: tasks[1]: 'ac' needs the velocity operator, which the 'lcao' model with
                 these inputs does not supply
    hint: LCAO is always non-orthogonal; velocity additionally needs the
          pseudopotential files
error: tasks[2]: 'ldos' currently requires a single Gamma point, but run.kpoints has 8
warning: run.npar: npar is 4 but there are only 2 k-points, so 2 sub-communicators
                   have nothing to do
```

Warnings do not stop a run; errors do, and `rsatb run` refuses to start rather
than failing partway through setup. `rsatb check --json` prints the same report
as a machine-readable document.

## Choosing a model

| your input | `model.type` | |
|---|---|---|
| Slater-Koster parameters you write | `sktb` | orthogonal unless `overlap` is given |
| Hamiltonian file + `.orb` + `.upf` | `lcao` | always non-orthogonal |
| a directory of DFTB `.skf` files | `dftb` | always non-orthogonal |
| a Hamiltonian file, already orthogonal | `tb_file` | must be told its basis |

`tb_file` is the only one that must be told its basis, because the supported
file formats carry no basis header. Every other model reads it.

Which observables are available follows from the model, and `check` reports it
before anything runs:

| | overlap | velocity | position |
|---|---|---|---|
| `sktb`, no `overlap` | — | yes | yes |
| `sktb` with `overlap` | yes | — | — |
| `lcao` | yes | with `.upf` | yes |
| `dftb` | yes | — | — |
| `tb_file` | — | yes | yes |

`ac`, `dc`, `dc_spectrum` and `quantum_metric` need velocity. `msd` needs
position, an orthogonal basis, and the Gamma point. `ldos` needs the radial
orbital files, so LCAO, at a single Gamma point.

## Structures

```json
"structure": {"file": "POSCAR"}
```

```json
"structure": {
  "positions": [[0.0, 0.0, 10.0], [0.0, 1.42, 10.0]],
  "symbols": ["C", "C"],
  "cell": [[2.4595, 0.0, 0.0], [1.22975, 2.13, 0.0], [0.0, 0.0, 20.0]],
  "pbc": [true, true, false],
  "supercell": [4, 4, 1]
}
```

Coordinates are used exactly as written. Nothing is wrapped, sorted or
renumbered on the way in, because atom order and coordinates are what a
Hamiltonian file's own indexing and R-vector convention refer to. Atoms may sit
outside the cell — the second carbon above is at fractional (-1/3, 2/3) — and
periodic images are expressed against the coordinates as given.

`supercell` belongs to the structure and tiles immediately before graph and
operator construction. Parameterized SKTB/DFTB operators are built directly
on the expanded geometry. For `lcao` and `tb_file`, a DeePTB HDF5 Hamiltonian
is read in primitive `(i,j,R)` indexing and mapped into the expanded cell on
the fly; no repeated HDF5 file is written. Other file layouts must explicitly
define the same mapping before they can be combined with `supercell`.

## k-points

Written out, or generated:

```json
"kpoints": [[0.0, 0.0, 0.0], [0.5, 0.0, 0.0]]
"kpoints": {"mesh": [4, 4, 1]}
"kpoints": {"mesh": [4, 4, 1], "shift": [0.05, 0.0, 0.0]}
"kpoints": {"line": [[0.5, 0.5, 0.5], [0.0, 0.0, 0.0]], "points_per_segment": 11}
```

A mesh is Gamma-centred. A line interpolates each segment with its endpoints
included and does not repeat a shared vertex. Observables return one row per
k-point in the order generated, and `check` reports the resolved count.

## Tasks

Tasks run in order against one setup, so asking for several costs one setup
rather than several:

```json
"tasks": [
  {"type": "dos", "dE": 0.05},
  {"type": "dc_spectrum", "n_moments": 1024, "kernel": "costaper"},
  {"type": "msd", "n_steps": 100, "dt_fs": 10.0, "n_kpm": 1024, "axis": "x"}
]
```

Two runs of the same observable need a `label` to tell their results apart:

```json
"tasks": [
  {"type": "dos", "label": "coarse", "dE": 0.3},
  {"type": "dos", "label": "fine",   "dE": 0.01}
]
```

An empty `tasks` list sets the calculation up and reports the derived basis and
the spectral window without computing anything, which is the cheapest way to
check an input end to end. `rsatb run --dry-run` stops one step earlier still,
before any setup.

Every task is documented with `rsatb doc tasks.<type>`.

## Output

```json
"output": {"dir": "results", "prefix": "graphene_", "format": "npz", "summary": true}
```

Rank 0 writes one `.npz` per task, named for the task's label, plus
`summary.json`:

```json
{
  "input":   { ...the resolved input, defaults and all... },
  "setup":   {"model": "SKTB", "type_symbols": ["C"], "type_norb": [1],
              "cutoff_radius": [0.8], "capabilities": {...},
              "n_kpoint": 1, "n_rank": 4, "energy_bounds": [-8.6, 8.6]},
  "results": [{"label": "dos", "type": "dos", "seconds": 1.7,
               "scalars": {}, "arrays": {"dos": {"shape": [1, 400], ...}},
               "file": "dos.npz"}]
}
```

The summary is the record of the run: it holds the input as resolved, the basis
that was derived from it, the window the expansions were scaled to, every
scalar result, and the shape and file of every array. `"format": "json"` writes
the arrays as nested lists instead; `"none"` writes only the summary.

## Running in parallel

```bash
mpirun -n 64 rsatb run input.json
```

`run.npar` splits the ranks into that many k-point-parallel sub-communicators.
Ranks inside one sub-communicator share a k-point and divide the atoms, so
every rank must own at least one atom — a sub-communicator with more ranks than
the cell has atoms is refused with a message rather than run, and `npar` is the
knob that puts the spare ranks on k-points instead.

## Using it from Python

The JSON layer is importable, so a script can validate and run an input without
going through the command line:

```python
from rsatb.inputs import load_and_resolve, build_calculation, run_tasks

resolved, issues = load_and_resolve("input.json")
if any(issue.is_error for issue in issues):
    raise SystemExit("\n".join(str(issue) for issue in issues))

calculation, model, options = build_calculation(resolved)
results = run_tasks(calculation, resolved["tasks"], options)
```

`build_calculation` returns the same `RSATB` the Python API constructs, so an
input file can be a starting point that a script then goes beyond.

## Where the schema lives

One declaration, in `rsatb/inputs/spec.py`. The validator, the defaults, the
`rsatb doc` output and the exported JSON Schema are all walks over that same
tree, so a field is written once. `rsatb schema > rsatb.schema.json` exports it
for an editor or a generator that speaks JSON Schema.

## Examples

`examples/` holds one input per model family, plus a transport run and a full
research run. Everything they read is in `examples/data/`, so 01 through 05 run
as written; 06 is the one that needs a structure you supply.

```bash
rsatb run examples/01_sktb_graphene.json
```

`examples/estimate_matvecs.py` reads an input and reports the matrix-vector
product count its tasks will cost, before anything is queued -- the one thing
that has no place in an input file, because it is a cost model rather than a
calculation.
